## [V1.5.1] 2026-09-05（master）—— 换色不生效双修复（兼容性 + 并发竞态）

> 用户反馈："温柔青年真帅，但是每个形象的穿搭颜色都无法实现切换"。像素级探针（色相分桶统计换色前后 canvas 差异）在本地 preview 与生产 Chromium 均正常 → 锁定用户设备（Android 16 WebView / 微信 XWEB）特征，挖出两个真机必现根因。

### 1. 重染管线兼容性（outfit.ts）
- 原实现用 `createImageBitmap` + `OffscreenCanvas.convertToBlob`——部分 Android Webview/iOS 上不存在，抛异常被 catch 静默吞掉 → 纹理保持原生，**表现就是所有颜色点了没反应**
- 改为 `Image` 解码 + DOM canvas + `toBlob`（全平台可用），重染逻辑零变化

### 2. 并发加载竞态（avatar.ts，真机重载 1-3s 时必现）
- nginx 日志取证：用户 22 秒内连点色板 8 次；原 `applyStyle/applyVariant/swap` 无并发控制 → 多个 load 并发跑、每个都 `addChild` 自己的模型：**孤儿模型叠层 + 旧色模型后完成覆盖新色**，用户看到的就是"点了没反应/颜色不对"
- 修复四件套：
  - `AvatarSprite._enqueue` 加载串行队列：swap/applyStyle/applyVariant 同一时刻只允许一个重载
  - `_loadSeq` 会话号：过期加载完成后直接 `destroy`，绝不入舞台
  - `_appliedStyle/_appliedVariant` 以**加载开始时的快照**如实记录（防连点合并判重谎报）
  - `_swapNow` 收敛循环：加载期间意图又变了 → 用最新意图补一轮重载，直到舞台与意图一致
- 效果：快速连点自动合并到最新意图，最后一击必胜出

### 3. 验证
- 新增 [probe-style.cjs](../client/probe-style.cjs) / [probe-style-race.cjs](../client/probe-style-race.cjs) / [probe-style-prod.cjs](../client/probe-style-prod.cjs) 像素级探针：本地/生产双验证换色生效（Hiyori 蓝 6.2%→19.9%、粉 71.8%；Chitose 藏青 70%→军绿后蓝 0%）
- 快速连点探针：加载严格串行（start→done 成对），最终视觉与最后一次点击一致
- E2E T1-T10 全绿，零 console 错误；生产 index-CN7eN79U.js 已部署验证

## [V1.4.2] 2026-09-04（master）—— 真实换装收尾：误染三连修（花斑腿/藏青发/棕发丝）

> 用户反馈"穿搭和装饰位置不对，而且我想要的是换装"。V1.3.1 配饰+光环方案否决后，V1.4.0 起实现纹理级重染（服装整体换色、肤色零改动）。本轮 loop engineering 用"离线 atlas 校准 → 全图聚类取证 → 修复 → 复检"循环，修掉三处误染后上线。

### 致命 bug：保护矩形从未生效（M4 根因）
- `recolorPixels(d, st)` 只声明了两个形参，调用处 `recolorPixels(img.data, style, rects…)` 传的矩形被静默丢弃（esbuild 剥类型不报错）——V1.4.0 的 OUTFIT_PROTECT 一直是摆设，Natori 头发整片被染
- 修复：`recolorPixels(d, w, st, rects, avatarId)` 真正接收矩形并逐像素命中判断

### 取证方法（可复用）
- Natori drawable id 全是 `ArtMeshNN` 泛型名，按名字识别头发不可行 → 改用**离线校准**：对真实 atlas 跑重染，再用"残留蓝色聚类"反推漏保护区（被染粉后残留的深蓝=头发），逐区域网格 crop 目检标定矩形
- 意外发现：Natori 前发底层有**棕色发丝**（h20-45），纯深藏青规则护不住

### 三处误染修复（[outfit.ts](../client/src/live2d/outfit.ts)）
1. **Hiyori 腿部粉色花斑**（M3）：皮肤高光 h43-44 恰好越过暖色阈值 42，且皮肤与开衫同为奶油色（h25-45 无法按颜色区分）→ 每模型肤色阈值 `SKIN_RULE`（Hiyori h≤48/s≤0.5）+ 腿/臂/手硬矩形双保险

## [V1.1.0-opt2] 2026-09-03 01:12（分支 feat/render-optimize，未合入 master）

### 新增
- **Vite Module Worker 预取分流**（`client/src/live2d/prefetch.worker.ts` v3）：HTTP fetch + JSON 解析全部放 Worker 线程，主线程只负责 WebGL 上传与渲染；Hiyori 模型 17 entries / Natori 24 entries，预取延迟 50-120ms
- **纹理 LOD（Level of Detail）半图**：`scripts/build-lod-sd.ps1` 用 System.Drawing 半尺寸 bicubic 下采样生成 `*.sd.png`（原图 1814KB→512KB 约 28%，2504KB→751KB 约 30%），balanced/saver 档默认启用，高画质档保留原图
- **visibilitychange 后台暂停**：`document.visibilitychange` 监听器挂 `app.stop()/ticker.remove`，切回 `app.start()/frames=0`，避免标签页后台时 CPU 空转与切回瞬间 deltaTime 尖峰；HUD 展示 `paused(back)` 标签

### 关键修复
- **Blob URL XHR Status 0 根因**：pixi-live2d-display 内 `ModelSettings.resolveURL = url.resolve(base, path)` 会把 `blob:http://host/<uuid>` 错拼成 `blob:http//host/<uuid>`（冒号丢失）→ `XMLHttpRequest` 无法解析协议，最终抛 Status 0。修复策略：
  1. Worker 不再将 model3.json 字段替换成 Blob URL，保留原始相对路径；
  2. Worker 额外返回 `blobMap: {相对路径 → Blob URL}`；
  3. 在 `Live2DFactory.live2DModelMiddlewares` 的 `jsonToSettings` 之后注入 2 个一次性中间件：先用 `settings.json === model3对象引用` 把 blobMap 注册进 WeakMap，再实例级覆盖 `settings.resolveURL(p)` → 命中 blobMap 直接返回 Blob URL，未命中走原始 `url.resolve`（与库内置 `ZipLoader.upload` 写法完全一致，不碰原型）
- **Cubism4ModelSettings 实例级覆盖 vs 原型 patch**：最终采用实例级覆盖（而不是 `ModelSettings.prototype.resolveURL = ...`），原因：cubism4 模块 `Live2DFactory` 不挂 window，且原型方法无法通过 TS 静态导出枚举，原型 patch 既不稳也易在模块边界失效
- **AvatarSprite 接口对齐 App.tsx**：补齐 `.play()` / `.setPosition()` / `.walkTo()` / `.goHome()` / `.playSadReaction()` 兼容方法；`setMood` 内部通过 `internalModel.motionManager` 拿 state.speed 和 expressionManager
- **App 旧 ticker 回调兼容**：AvatarSprite.tick(delta) 改为 delta 可选（缺省 1 兼容 Pixi app.ticker.add 不传参）
