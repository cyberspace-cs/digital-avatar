## 2. 系统分层（与需求书第二十一节对齐）

```
┌─────────────────────────────────────────────┐
│  前端 (Vite+React+TS)                        │
│  ┌─────────┐ ┌─────────┐ ┌────────────────┐ │
│  │ Avatar层 │ │ Action层 │ │ State层        │ │
│  │ Live2D   │ │ poke/    │ │ happy/sad/...  │ │
│  │ 模型渲染  │ │ pat/hug  │ │ 视觉规则映射    │ │
│  └─────────┘ └─────────┘ └────────────────┘ │
│  ┌─────────────────────────────────────────┐ │
│  │ Event层：互动事件 → 本地播放 + Socket.IO  │ │
│  └─────────────────────────────────────────┘ │
└──────────────┬──────────────────────────────┘
               │ Socket.IO (ws)
┌──────────────▼──────────────────────────────┐
│  后端 (Express + Socket.IO)                  │
│  REST: 身份/关系/事件记录   WS: 事件实时推送   │
└──────────────┬──────────────────────────────┘
               │
        SQLite (users / bonds / events / states)
```

### 四层职责
- **Avatar 层**：Live2D 模型加载、渲染、拖拽定位、闲置行为（眨眼/呼吸/探头）
- **Action 层**：统一动作 ID（poke/pat/hug/heart/wave...），动作资源与角色解耦
- **State 层**：心情状态（happy/low/tired/angry），控制表情、动作速度、可见性
- **Event 层**：`event_id / sender_id / receiver_id / action_id / timestamp / state_snapshot / status / message`，动画播放失败不影响记录落库

## 6. 渲染性能优化（V1.1 分支 feat/render-optimize，2026-09-03）

> 背景：手机端实时渲染效果差（掉帧/发热）。本分支先落地桌面端零回归的通用优化，
> 手机端专项（Worker/OffscreenCanvas、LOD 纹理分级）作为后续阶段，证据先行。

### 6.1 调研证据（2026-09-03 联网调研）

| #   | 优化手段                                            | 证据来源                                                                                                                                                                               | 结论                                                  |
| --- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 1   | 渲染帧率上限 60→30，GPU 占用近似减半                | pixi-live2d-display 官方仓库 issue #50：用户实测 GPU 25%→约一半，作者 guansss 回复"trade-off 是可行方向"                                                                               | 采纳：自适应帧率治理                                  |
| 2   | `antialias: false` 对弱设备提升明显                 | PixiJS 官方 Performance Tips（7.x 文档）："older mobile devices… `useContextAlpha: false` and `antialias: false` can help"                                                             | 采纳：初始化关闭 MSAA                                 |
| 3   | `resolution` 决定填充率，应跟随 DPR 且封顶          | PixiJS 官方（Text resolution 说明）+ untitled-pixi-live2d-engine #15（resolution 与 DPI 不符导致锯齿/性能问题）+ kako-jun/name-name #279（未设 resolution 导致 canvas 逻辑分辨率渲染） | 采纳：`resolution: min(dpr, 2)` + `autoDensity: true` |
| 4   | 多模型场景开销 = Draw Call 数量，降帧按比例降低     | Live2D 官方 FAQ（多模型 SetPass/绘制调用增加）                                                                                                                                         | 采纳：双人同屏时同样受益于帧率档位                    |
| 5   | 加载卡顿优化：异步解析 / Worker+纹理分发 / LOD+缓存 | CSDN 问答实测（iPhone 8 + 6000 面：主线程阻塞 820ms→90ms，FPS 60→18 提升到 60→54）                                                                                                     | 第二阶段采纳（架构级改造）                            |
| 6   | Mask 预处理/多 mask 纹理                            | Live2D 官方 Mask pretreatment methods (Web)（R6+ 特性，SDK 默认已用预处理法保手机帧率）                                                                                                | 已由 Cubism SDK 内建，无需改动                        |

### 6.2 已落地（本分支）

1. **PerfGovernor 自适应帧率治理**（`client/src/live2d/perf.ts`）
   - 三档位：high=60fps/2x res、balanced=30fps/1x、saver=20fps/1x
   - 每 4s 统计实际 FPS，低于档位目标 75% 自动降档；触屏设备默认 balanced 起步
   - `?perf=high|balanced|saver` 强制指定；`?fps=1` 显示调试 HUD；`localStorage.da_perf` 持久化
   - 实测（本地 dev，DPR 1.5 显示器）：high 档稳定 55-58fps 未降档；balanced 档 28fps
2. **初始化参数优化**（`client/src/App.tsx`）：`antialias: false` + `resolution: min(dpr,2)` + `autoDensity: true` + `powerPreference: 'high-performance'`

### 6.3 第二阶段（手机端专项，已落地 V1.1.0-opt2）

> 本节 2026-09-03 原"规划"已实施。代码改动集中在 `client/src/live2d/{prefetch.worker.ts, avatar.ts, perf.ts}` + `scripts/build-lod-sd.ps1`。

1. **Worker 预取分流（Vite Module Worker）**
   - 机制：App.tsx → AvatarSprite.load() → 动态 `import('./prefetch.worker.ts?worker')` → postMessage `{kind:'prefetch', modelUrl, lod}`
   - Worker 内 fetch model3.json（设置 `json.url = baseDir`）→ 收集 FR.Moc / Textures / Motions / Expressions / Physics / Pose / UserData / DisplayInfo → 并发 `fetch` 封装 Blob → `URL.createObjectURL`
   - 传回 `{model3, blobMap:{relPath→BlobURL}, blobUrls[], timings}`
   - **坑与修复（关键证据）**：
     - v1 直接把 Blob URL 写回 model3.json 字段 → 库 `url.resolve(base, blob:http://X)` 错拼成 `blob:http//X`（冒号丢失） → XHR Status 0 FAIL
     - v2 通过 `Live2DFactory.live2DModelMiddlewares` 在 `jsonToSettings` 之后插入 2 个中间件：
       ① 用 `settings.json === model3对象引用` 匹配 → 注册 `blobMap` 到 `WeakMap<settings, Map>`
       ② 实例级覆盖 `settings.resolveURL(p)`：命中 blobMap 返回 Blob URL，未命中走原始 `url.resolve`
     - 此写法与库内置 `ZipLoader.upload` 的 `settings.resolveURL = function(...)` 模式一致，无原型污染、无模块边界失效风险
   - 结果：新标签页 Hiyori 17 entries 60-90ms / Natori 24 entries 70-110ms；控制台 0 条 `blob:http//` XHR / Status 0 / TextureLoadingError

2. **纹理 LOD（Level of Detail，半尺寸 SD）**
   - 生成：`scripts/build-lod-sd.ps1`（PowerShell System.Drawing，依赖 sharp/canvas 重模块），半尺寸 bicubic 下采样 + 增量跳过
   - 产出：Hiyori×2 / Natori×1 / Haru×2 共 5 张 `*.sd.png`；2048px→1024px，体积缩约 70%
   - 接入：`tier != high` 时 Worker 把 PNG URL 换成 `foo.sd.png`，fetch 失败自动回落到原图（保障不会白屏）

3. **visibilitychange 后台暂停**
   - `PerfGovernor` 构造时 `document.addEventListener('visibilitychange', this.onVisibility)`
   - 切后台：`app.stop()` + `ticker.remove(this.onTick)` → CPU/GPU 完全停
   - 切前台：`app.start()` + `ticker.add(...)` + `frames=0` + `windowStart=now` → 避免 deltaTime 尖峰
   - HUD 在 `backgroundPaused===true` 时显示 ` · paused(back)` 后缀
   - 备注：自动化 Electron/OSR 环境因共享渲染进程不触发 visibilitychange 事件，代码正确需真机手动复核

4. **移动端起步档位**：`isMobileDevice()`（`matchMedia('(pointer:coarse)')` + UA）为 true 时默认 `balanced` 档 + LOD sd 纹理

## 7. 已识别风险

| 风险                                 | 对策                                                                     |
| ------------------------------------ | ------------------------------------------------------------------------ |
| 双人拥抱需两模型同屏                 | 同一 Pixi Application stage 加两个 Live2DModel，独立控制位置/缩放/zIndex |
| 状态"互动后发现"需拦截默认反应       | 事件处理时先查 receiver 当前状态，命中规则则替换反应脚本                 |
| Cubism Core 不可再分发               | 仅本地开发使用 + 服务器部署时单独 scp，不进公开仓库（.gitignore）        |
| pixi-live2d-display 与 Pixi 版本耦合 | 锁定 pixi@6.5.10 + pixi-live2d-display@0.4.0                             |
| Blob URL 生命周期泄漏                | `AvatarSprite.destroy()` 遍历 `this._blobUrls` 统一 `URL.revokeObjectURL` |
| Worker 中间件栈内存泄漏              | settingsBlobMap 使用 WeakMap，实例销毁后自动 GC                          |

## 8. 小火人化：App 壳 + 火花成长体系（V1.2，2026-09-04）

> 参考"抖音小火人"玩法，把应用从网页工具升级为高互动陪伴 App。设计 spec：`docs/superpowers/specs/2026-09-04-xiaohuoren-gamification-design.md`

### 8.1 App 壳（前端形态）
- 底部 4 Tab：🏠陪伴（Live2D 舞台 + 关系卡 + 互动 Dock）/ 🎯任务 / 💞记录 / ⚙️我的
- **Pixi 舞台常驻不卸载**：切 Tab 仅用面板覆盖（`position:fixed` + z-index），避免 Live2D 模型重复加载开销
- **PWA**：`client/public/manifest.json` + SVG 图标 + `viewport-fit=cover` / `theme-color`——手机"添加到主屏幕"后 standalone 全屏启动

### 8.2 火花成长体系（服务端权威，防刷）
- **数据模型**（`server/src/db.js`，幂等迁移 try/catch）：
  - `bonds` 加列 `growth / streak / last_active_day`
  - 新表 `growth_events(id, bond_id, delta, reason, day, created_at)` + 索引 `(bond_id, day)`；`quest:<id>:<day>` 形式的 reason 兼作任务判重幂等键
- **结算规则**（`server/src/index.js` 内联于 `interaction` socket handler，单 bond 单事务流）：
  - 火花：互动 +1（每日 30 次封顶）、喂食/送花 +2（每日各 5 次）；`SPARK_RULES` 配置驱动
  - 等级：`LEVELS` 7 级（火种 0 → 永恒 6000），`levelOf()` 纯函数
  - streak：`last_active_day !== today` 时，昨日有活跃则 +1 否则重置 1；不删数据，断联仅软惩罚（前端 `cold` 状态：火花灰化 + 分身沮丧表情），互动立即复燃
  - 每日任务：`questCountsToday` 按 bond 当日 events 统计（互动≥5 / 说话≥1 / 喂食≥1），达标即写 `quest:<id>:<day>` 流水 +10，天然判重
- **实时同步**：结算完成后向双方 socket 推 `growth_update`（含 bond 元数据、本次 delta、`leveledUp` 升级信号）
- **新 API**：`GET /api/bond/:userId`（关系卡初始化/刷新）、`GET /api/quests/:userId`（任务进度）
- **前端消费**（`App.tsx`）：关系卡（等级徽章 + 连续天数 + 进度条）、升级 toast、Dock 点击本地粒子反馈 + socket 同步；`bond.cold` 驱动断联视觉
